# Decisions

## 2026-11-14: harnesslang starts from tempolang's method and nanocode's durability

harnesslang takes tempolang's method (an interpreter as the executable spec, generated code checked against it, deterministic simulation from a seed, invariants as compiler checks) and applies it to nanocode's problem: making an agent harness durable on hosts that promise different things. The journal follows nanocode-turnlog's records, the effect classes are nanocode's `EffectClass`, and the simulator's invariants, fault profiles and mutation discipline are nanocode-sim's, so that nanocode is the oracle.

The compiler is one std-only Rust crate. Generated programs are std-only too. Targets are models in `src/target/` that the checker, the lowering and the simulator share.

## 2026-11-14: the core: parser, checker, IR, replay interpreter, target models and simulator

`src/syntax` lexes and parses the language of `docs/ARCHITECTURE.md` with an explicit nesting bound (`NESTING_DEPTH_MAX` = 64, policy: deeper than any harness we write, shallow enough for the default thread stack). `src/check` resolves names and types, proves matches exhaustive (a `maybe` match without `unknown` names the reason), requires every loop and list capacity to be a named constant and lowers straight to `src/ir`. `src/ir` holds the lowered program, its validation (pair assertions: every site placed exactly once, durability follows class) and the worst-case walk. `src/run` is the replay interpreter, the journal (JSON lines with CRC-32, own JSON codec and CRC) and the session fold. `src/target` holds the five target models and the storage media the simulator drives. `src/sim` is `hl sim`. `hl emit` exists and fails with "not yet" until `src/emit` is built.

Decisions the spec left open:

- Journal lines are `{"crc":N,"record":R}`; `R` follows nanocode-turnlog's `Record` field for field so serde decodes it: `admitted` (digest = handler name, first = 1, the first sequence number of a turn, hand = null, metadata = {handler}, prompt = the arguments by name), `call`, `result`, `model`, `recovery`, `status` (always `finished`, outcome `completed` or `failed`), `checkpoint` (payload is the state as JSON text, state is the harness name, revision is the turn it follows). `call`, `result` and `model` add `seq`, which serde ignores. Call ids are `turn/seq`.
- The model writes only a `model` record; `now` and `random` write `call` and `result` with tool names `now` and `random`. Worst-case records per effect are 2 (model 1), plus admitted, status and checkpoint per turn; recovery records are one per restart and are reported apart.
- Effects are hoisted out of expressions: a statement's effects run first, left to right. `and`/`or` evaluate both sides. No shadowing. A variant constructor takes its type from the expected type, else from the one sum that has it, else it is an error naming the candidates. State fields need a zero value (u64, bool, text, list). Tools return u64, bool or text so the simulator can produce results. `reply` and `entry` need a model.
- Every finish writes a checkpoint in the same flush. State before a turn is the latest checkpoint plus replay of any finished turns after it (a torn checkpoint line is recovered by replay). The simulator also checks that replaying the whole journal from nothing gives the same state.
- Recovery is `AtLoad` (the runner turns open external calls into a `recovery` record before the handler runs) everywhere but Vercel, where it is `InStep`: the external step reads a durable attempt counter and returns `unknown` on any attempt after the first, writing a `recovery` record for that one call. Recovery attempts number per turn.
- Cloudflare commits before every outbound request (the output gate) and before the response; Vercel also commits each external step's result when the step returns; Postgres takes a new owner epoch on every run and refuses a flush from an older epoch; JSONL fsyncs on open before trusting what the page cache shows, then truncates a torn tail.
- Acknowledging a finish checks that its status is durable at that moment; that is how `finish_once` sees an early acknowledgement whose outcome happens to repeat.
- `world.medium.durable().ok()?` in the simulator treats an unreadable durable journal as "no durable status" when an acknowledgement is checked, which reports the acknowledgement as a `finish_once` violation; the unreadable journal itself is reported by `liveness`.

Simulator policy constants (src/sim): `TURNS_PER_SESSION_MAX` 4, `RESTARTS_PER_TURN_MAX` 12 (after the budget a run is fault free, so `liveness` fails only on a bug), `RUNS_PER_TURN_MAX` = restarts + 2 (the clean run and a fenced old owner), crash probability per hook 2% to 25% per seed, torn writes and crashes between write and fsync up to 30%, power loss on a crash 30% to 100% in the async and lying profiles, half of unsynced 512-byte sectors persisted in the lying profile, lease expiry 2% to 10% per hook in the Postgres lease profile, model answers 35% of the time, 25% of requested tools undeclared, 0.5% of replies over the calls bound (the handler then fails with `bound`), 15% of tool runs fail. Profiles: 3 in 10 seeds clean, the rest errors (JSONL: also async 2 in 10 and lying 2 in 10; Postgres: lease 4 in 10). JSONL "lying" here means a power loss that persists unsynced sectors out of order, the unpersisted ones reading as zeros.

## 2026-11-14: the nanocode oracle, the panic invariant and recovery_skipped

`oracle/` is its own Cargo workspace (`oracle/target` ignored) and the one place with outside dependencies: `nanocode-turnlog` by git from https://github.com/nanocodexyz/nanocode at 395967ffd227ef2158ea824df6ee4c6054d30293 (the reference checkout's HEAD; GitHub's HEAD was 83489e4 the same day), `serde`, `serde_json` (raw_value) and `crc` (its CRC_32_ISO_HDLC catalog entry, so the checksum is computed by code that is not ours). `oracle/Cargo.lock` was seeded from nanocode's own `Cargo.lock`, so the oracle builds the versions nanocode pins (serde 1.0.228, serde_json 1.0.150, tokio 1.52.3), and `[patch.crates-io] serde_derive` points at nanocode's own derive crate as nanocode's workspace does: a git dependency's patches do not reach the depending workspace, and without the patch Cargo resolved serde 1.0.229 with crates.io's serde_derive, syn, quote and proc-macro2 (38 packages instead of 34). tokio, mio, socket2 and the futures crates arrive through nanocode-turnlog's own dependencies; the oracle uses none of them.

What it checks (`hl sim --dump-journal DIR` writes `<example>-<target>-<seed>.jsonl` and `.summary.jsonl`, the interpreter's `run::session` fold after every record; `hl-oracle DIR...` compares):

- Line rules: the oracle's own reader (serde envelope, `crc` crate, stop at the first failing or unterminated line; for rows, every line must be JSON) must read exactly the records the interpreter's `decode_lines` reads.
- Every record decodes as `nanocode_turnlog::Record` and applies to a `nanocode_turnlog::Fold` (with no row, so `next_attempt` is attempt + 1) exactly when `session::apply` accepts it.
- After every record, for the turn it touched: phase (nanocode's Queued or Running is our running), outcome, last, result, digest and prompt, recovery attempt, model replies, open calls with classes, the external open calls a recovery must report unknown (`Fold::unknown` of that turn), and every call's class. The comparison runs at every prefix because every load the interpreter makes is a prefix of the final journal (JSONL truncates a torn tail and appends; rows only append).
- Before a call record: its class is nanocode's `Effects::default()` over the program's declarations plus `now` and `random` as none (`Effects::builtin()` is nanocode's own tool list and does not apply). Before a recovery: its attempt is `next_attempt`; at load it lists exactly the open external calls of its turn, in step (Vercel) exactly one of them. Before a status: nanocode holds no call of that turn open. At the end of a passing seed every turn is finished and nothing is open.

Journals and summaries take 1.2 GB in output/; `hl-oracle` reads them in 7.5 s on one core.
- Default `scripts/oracle.sh` (seeds 0..500, 7,500 journals, 409,107 records, then five mutation runs of agent.hl seeds 0..200): 8.6 s. `HL_ORACLE=1 scripts/check.sh`: 43 s end to end.
- Disagreements on unmutated journals: none, so nothing to fix on either side. Under mutations the oracle disagrees with postgres_no_fence (67), idempotent_reported_unknown (38 on jsonl, 240 on cloudflare) and rerun_rewrites_call (38, 240), which `scripts/oracle.sh` requires; jsonl_no_checksum's torn journals are refused by both readers alike (39 of seeds 0..100). The other seven mutations write journals both folds read alike: their bugs show only against the world (dispatch counts, acknowledgements), which a journal does not hold, so the simulator's invariants remain the only check for them.
- Every mutation disagreement is nanocode's fold being more permissive than ours, not a bug on either side, so nothing was reported upstream: `Fold::apply` accepts a result for a call that is not open or whose turn finished, a second `admitted` for a finished turn id (it replaces the turn), a `call` for an id already open (it overwrites it) and a recovery listing calls that are not open external (it removes them). nanocode's single writer is what keeps those out of its logs; harnesslang's session fold refuses them.

nanocode-sim's turn scenario against ours. Invariants: it has external_once, finish_once, idempotent_known, in_object_once, liveness, panic and seq_unique. in_object_once (a workspace write or spawn committed inside the object's transaction applied once) has no harnesslang counterpart until there is an in-object effect such as `spawn`. panic was missing: a broken assertion aborted `hl sim` with no seed. `run_seed_traced` now catches the panic at the seed boundary and the sweep reports `FAIL invariant=panic` with the seed and replay command; the assertion still panics, as TigerStyle wants, and the default hook still prints where. Mutations: finish_before_row and durable_seq_before_commit (telling a client something is durable before its commit) are our finish_before_flush; gate_releases_early and idempotent_reported_unknown are ours already; retire_skipped and seal_skipped are compaction, which harnesslang does not have yet; tick_not_atomic has no counterpart that could be caught, by argument rather than simulation: our flushes are ordered and any prefix of one is a state a torn JSONL group commit already produces. recovery_skips_clientless becomes `recovery_skipped`: at-load recovery reports nothing (every harnesslang rerun is a restart without a client, so it skips all of them). It shares `recover`'s path with recovery_redispatches_external but is not exempt from the engine's assertion that recovery turns every open external call unknown before the turn runs again, so the panic invariant catches it at seed 0 on native-jsonl, native-sqlite, server-postgres and cloudflare (not Vercel, whose recovery is in step). `scripts/mutations.sh` runs it and now prints each mutation's FAIL line rather than the first line of output.

## 2026-11-14: a kill -9 crash drill for native-jsonl generated code

`scripts/rust-crash-drill.sh` emits examples/agent.hl for native-jsonl, compiles it with `scripts/rust/drill_host.rs` (a host whose tools append a synced ledger line before they run and whose acknowledgements append a synced line) and runs each session's process repeatedly, sending it kill -9 after 0 to `DRILL_DELAY_MS_MAX` ms until a run exits 0. Then it checks the real files: external_once, unknown_reported, idempotent_known, finish_once, every acknowledgement matching its status. Defaults: 16 sessions of 6 turns, 12 ms, 400 kills per session (policy: about 7 kills a session on this Hand, well under the cap). `DRILL_SEED` offsets the seeds, and any failure exits non-zero and prints `drill: FAILED` on stdout, so a pipe hides nothing. `HL_DRILL=1 scripts/check.sh` runs 4 sessions, then requires `DRILL_MUTATION=flush_after_dispatch` (the generated code with its flush before an external effect removed by sed) to fail with an external call that ran before its call record was durable, or whose id was reused for another tool after that record was lost. It caught the mutation in 32 of 32 trials, at session 1 or 2.

The first version failed with "idempotent 6/37 ran before any call record". This was the drill's check, not the generated code. In a killed run, idempotent `edit` ran at 6/37 after 6/35 and the model at 6/36, with none of their records flushed, which durability point 3 allows. The kill lost them, and after recovery the model ran again and answered, so 6/37 was never asked for again. The drill's model is seeded from the clock, so a model that is run again can answer differently, as a real one can. The check now models the spec exactly. Each run writes a `run` marker to the ledger. External dispatches, from any run, need a durable call record for the same tool and run once. None and idempotent dispatches in the run that exited 0 need a durable call record for the same tool, because the status flush covers every buffered record (point 2). Those in killed runs may be missing (point 3). Every none or idempotent call record has a result, and that result has a dispatch of its id and tool in some run (`now` and `random` excepted). The engine already asserts that a call record is durable before its external effect runs, and `flush_after_dispatch` covers that in `hl sim`, so no new mutation was needed.

Measurements (5-core Linux Hand shared with another agent): 12 full default drills with seed bases 0 to 1200, all passing, 1,033 kill -9s over 1,225 runs, 41,779 records, 8,962 external calls (616 reported unknown), 8,611 none or idempotent calls, and 72 none or idempotent dispatches lost in a kill and never recorded. A default drill takes about 1.5 s; `HL_DRILL=1 scripts/check.sh` took 21 s end to end. Known limit: `run_jsonl` reopens and folds the whole journal for each turn, and every checkpoint holds the whole state. At 24 turns, one restart takes 39 ms just to pass 12 finished turns, so a 30 ms kill delay stops all progress (400 kills, stuck at turn 12). This is restart cost, not durability. It needs a checkpoint-bounded open before longer drills.

## 2026-11-14: the prover: push_bound is an error, an independent worst case, prove-mutations and a soundness audit

`src/prove` (committed in f3d94d4 by an agent whose notes were lost) proves, per handler and target, the properties `docs/ARCHITECTURE.md` lists under Proofs. This entry records what was established on top of it.

- **push_bound is an error.** It was a warning, so `examples/minimal.hl` "proved" while every push in it could trap with `bound(history)` (counterexample `len(history) = 256`), and the report printed the handler's arithmetic as proved. That contradicts the goal that a proving program does not trap in its own code: `no_overflow` was already an error, and a full list is the same kind of failure. A push is now an obligation like any other, `Severity` is gone (every finding is an error), and `examples/minimal.hl` gains `requires len(history) + 1 + steps_max * (1 + calls_max) <= history_max` (41 of 256 entries per turn), the form agent.hl and reviewer.hl already use. Once history lacks room the handler refuses the turn with `requires(ask)`, which is the honest behaviour until compaction exists. `examples/invalid/over_cloudflare.hl` gains the same kind of `requires` so it still proves on every target but Cloudflare, which is what it is for.
- **worst_case was not the prover's own.** It compared `ir::worst`'s count with the limit, so the property was reported proved from a number the prover never derived. The prover now counts the longest path of outbound runs in its own plan (choices take the widest arm, loops multiply by their bound) and asserts that `ir::worst` is not below it, a pair assertion between two computations of one bound. They agree on every example: 1,088 (agent), 40 (minimal), 57 and 0 (reviewer), 17,408 (over_cloudflare).
- **The audit found no other unsound proof.** Read: the plan walk (every choice entered from every state, loops iterated to a fixpoint within their bound, `End` checks the phase), the finish walk, loop summaries (the body runs once with the changed quantities free; `modified` covers every way a quantity changes, since locals are never reassigned and `push` targets fields only; `for` counts the list's length at entry, matching the interpreter's snapshot; a body that never falls through yields no exit for `loop` and an empty list for `for`), joins (only facts both sides imply, plus hulls), and the solver (gcd tightening rounds the constant up, box subsumption only drops implied constraints, every `Overflow` or `Budget` result is taken as "not proved" or "feasible", every failed projection drops facts). Traps the interpreter can raise are `requires` (state unchanged), overflow and full pushes (both obligations now) and an undecodable model reply (invariants checked there). Then probed with adversarial programs; each class now has an invalid example that `scripts/prove-mutations.sh` requires to fail with its message: `overflow_counter`, `underflow_elapsed`, `loop_overflow` (only the seventh addition overflows), `product_overflow`, `branch_overflow` (overflow on one side of a join), `push_unbounded` (the old minimal.hl), `push_unknown_arm` (the `unknown` arm of a dispatch pushes twice), `push_self_iteration` (a `for` over the list it pushes onto), `push_early_return` (a loop that returns on some paths), `invariant_return` (nested loops), `invariant_trap` (a counter restored before return but left raised when the model reply fails to decode), `invariant_initial` and `invariant_unsupported` (an invariant over a `bool` fails instead of being assumed). Durability and finishing bugs cannot be written in a program, since the compiler places every flush and `hl check` already refuses a handler that can reach its end; the mutations cover them.
- **Known imprecision, not unsoundness.** Counterexamples are solutions of the prover's facts, not replays: `branch_overflow` reports `base = 18446744073709551606` from the hull of 5 and 18446744073709551610, and a loop's summary can report values no run reaches. The loop summary keeps a per-iteration change, not a closed form, so `x = x + step` over `loop step below 8` bounds `x` by `[0, 56]` rather than 28, and `x - 28` after it fails.
- **scripts/prove-mutations.sh**, run by `scripts/check.sh` right after `scripts/mutations.sh`: every example proves; for every mutation `hl prove` lists (16: the simulator's 12 lowering mutations and `drop_flush`, `drop_finish`, `drop_requires`, `repeat_assign`), proving agent.hl and reviewer.hl fails on every target it applies to, with exit 1 and the property the script expects for it (a mutation without one fails the script); and the 13 invalid examples fail with their exact message. Mutations run in parallel, one process per mutation.

Measurements (5-core Linux Hand shared with another agent, rustc 1.100.0, release build, mean of 20 runs, all five targets): `hl prove` examples/minimal.hl 6.6 ms, examples/agent.hl 11.3 ms, examples/reviewer.hl 194 ms (186 ms on one target: the arithmetic proof, 70,913 elimination steps for `review_change`, dominates and is target independent; agent.hl takes 4,098 steps, minimal.hl 3,227). `scripts/prove-mutations.sh`: 11.1 s sequential, 3.3 s with one process per mutation.

Commands: `target/release/hl prove [--target T] [--mutation M] FILE`, `scripts/prove-mutations.sh`.

## 2026-11-14: code mode design (docs/CODE_MODE.md)

Code mode is specified, not built: `docs/CODE_MODE.md` holds the `code` declaration, the IR additions, the cell journal, recovery and placement per target, the simulator's faults and invariants, the prover's obligations, the mutations and the oracle's checks. It follows nanocode at 395967f, read on 2026-11-14 in /home/hand/ref/nanocode: `crates/runtime/code-mode/src/code_mode/replay.rs` (`CellJournal`, `CellJournalUpdate`, `JournaledCall`, `CellJournal::fold`, `UNKNOWN_OUTCOME`, `unknown_outcome()`, `divergence_text`), `code_mode/mod.rs` (`Nested::Recover` falling back to the unknown outcome, `resume_replayed`: queued calls dispatched, running calls without an outcome recovered, `CellGuard`, `Limits.nested`), `crates/runtime/code-mode-engine/src/journal.rs` (`JournalEntry`, `same_step`, `JOURNAL_LIMIT_BYTES` 32 MiB), `crates/runtime/agent/src/one_log.rs` (`OneLogJournals::save`: a row commits when an update carries a running call whose tool `needs_row()`, or a `Timeout` while the header is new or unsaved), `crates/core/turnlog/src/{record,fold}.rs` (`Record::Cell`, `Record::Forget`, `Fold::unknown` = every open external call) and nanocode's DECISIONS.md entry of 2026-11-14 on first saves (rows per turn: reply 2, `text("ok")` cell 2, timer cell 3, `tools.charge` cell 3). `code_mode_policy.rs` in the Claude and Codex backends only routes workspace tools and marks writers exclusive, which harnesslang's nested tools do not need. durable-cloudflare runs cells in the session's Durable Object (nanocode-ts's djs wasm, cell memory 32 MiB, half of the 64 MiB runtime budget); durable-vercel in the Function; both moved to the first-save rule on 2026-11-14 and their drills pass.

Decisions the design takes:

- The engine is an interface (nanocode's journal protocol), not part of harnesslang: a std-only compiler cannot embed djs. Native hosts bind djs; the simulator has its own deterministic engine whose cells also carry their JavaScript, so `oracle/` runs them in djs and compares the `JournalEntry` streams.
- Cloudflare runs a cell in a Worker Loader isolate with `globalOutbound: null`, so the isolate cannot send anything the output gate does not hold; Vercel runs it in the re-executed workflow function with each nested call a step. Both rest on platform facts not yet read from the vendor pages (listed in CODE_MODE.md); where one is false the target refuses `code` rather than weaken at-most-once.
- The code site's own `call` record is class `none`: the cell is replayable and its external work is journaled per nested call. nanocode's `Effects` must declare code tools `none` in the oracle.
- `calls` bounds nested calls across all tools (nanocode's guard is per tool), so the prover multiplies one number.
- harnesslang writes the nested `call` record's `turn`, which nanocode leaves `None`; no `forget` or `stored` records.
- No yield or `wait` yet: a turn blocks on its cell; the header carries `yield_time_ms` for nanocode's fold.
- Simulator policy: cells in 20% of tool-call replies, engine divergence in 1% of replays.

No code changed, so there is nothing to measure; `scripts/check.sh` passes on this commit as on its parent.

## 2026-11-14: native-jsonl opens from the last trusted checkpoint, and the drill client resumes from its last acknowledgement

The generated native-jsonl runtime no longer reads and folds the whole journal on every turn. `jsonl_open_tail` fsyncs, reads backward from the end in windows that start at `PAGE_BYTES` (4096, the Linux page size, the unit the page cache reads) and double, and stops at the last checkpoint line that has a valid CRC and any byte after its newline. It decodes forward from that line with the same line rule as before (a failing or unterminated line ends the journal and is truncated, then synced) and folds from the checkpoint (`Start::Checkpoint`, `fold_from`, `run_turn_from`), so an open costs the checkpoint plus the work after it. `JsonlJournal` keeps that tail in memory across the turns of one process: after a finished turn its tail is the checkpoint it just synced, so a process running many turns never reopens. A request for a turn at or before the tail's checkpoint reads the whole journal (`jsonl_open_for`, and `JsonlJournal::run`), since only the whole journal holds that turn's status. The durability points, flushes, records and bytes written are unchanged: `drill_host bench` writes the same records with the same fsyncs before and after.

Why a checkpoint needs a byte after it. Every flush is one append then one fsync, a failed fsync ends the run, and an open syncs and truncates to the valid prefix before anything is appended, so only the last flush group can hold a torn, zeroed or out-of-order line (the lying profile in `src/target/medium.rs` loses only unsynced sectors). A checkpoint is always the last record of its finish flush, so any byte after it was appended after its group's fsync returned: that checkpoint and everything before it are durable and valid, and reading from it gives exactly what the whole read gives. The last checkpoint at the end of the file may belong to an unsynced group whose earlier lines are zeros, so the open goes back to the one before it. This trusts what was synced before a verified checkpoint, as nanocode-turnlog does; corruption of synced bytes in the middle of a file is in no target's model, and only a whole read would notice it. The scan's opening test is checked once per process (`jsonl_self_check`), and the drill's verify now requires the tail open to fold every turn after its checkpoint as the whole open does and an older turn to read the whole journal.

## 2026-11-14: a return ends its path in the worst case, paired with the plan's record count; ARCHITECTURE.md matches the code

`ir::worst` now computes, for every block, the worst cost of the paths that fall through it and of the paths that end in it, separately. `Finish` ends its path; a sequence adds the second part only to paths that fell through the first; `if` and `match` take the widest of each; a `loop` of bound N counts N full iterations for falling through and N - 1 full iterations plus the worst ending one for a return inside it, and a `for` may also run zero times. Before, a `return` counted as if execution continued after it, so a `return` inside a loop added its two finish records once per iteration, and the effects and outbound requests of a loop whose body always returns were multiplied by its bound. The three measures are exact over the statement tree now (they still take branches the conditions may rule out).

Pairing. The prover counts journal records again on each target's lowered plan (`planned` in `src/prove/mod.rs`), with the same path rule over `Op::End`, and the outbound count it already compared now uses it too. `Op::Repeat` carries `every_iteration` (true for `loop`, which the interpreter runs to its bound unless it returns) so the plan count knows a `loop` whose body always ends cannot fall through. The plan's records must not exceed the IR's on any mutation, and for an unmutated program must equal it, since the first run of the IR's longest path is a path of the plan (reruns write a `recovery` record in place of `admitted`, and a reopened call writes no more than a fresh one; trap arms finish no later than a return would). `hl prove` and `hl check` report it per handler and target as `worst_case: N journal records per run on the plan's longest path, as hl check counts`.

## 2026-11-14: text enums, checked at every boundary

`type status = "completed" | "failed" | "interrupted"` declares a text enum (GAPS.md gap 10, now removed). It is a parameter, state field, tool result and handler result type. A text literal is a value where the enum is expected, and an unlisted literal is an error. `match` takes one text arm per value and is exhaustive like a sum's. `==` refuses text enums, and there is no conversion to `text`. A state field starts at the first value. The journal holds the text: the `admitted` prompt, checkpoint fields and `result` outputs are JSON strings.

How it is built, kept local to the front end where possible:

- The AST gains `TypeBody::Values` and `Pattern::Value`. The IR lowers a text enum to an `ir::Sum` of fieldless variants named by their texts, marked `SumKind::Text`, so the interpreter, the prover, `ir::worst` and every emitter's match and construct code take it as an ordinary sum. The existing fieldless-variant JSON encoding already writes the text, and the existing variant decoders already refuse an unlisted name. Name-based constructor lookup, and the check that a tool name is not a variant name, skip text enums, so the value "completed" and a variant `completed(text)` do not collide.
- `Value::zero` takes the program, so a text enum state field has a zero value: its first value.
- Boundary rule, the same in the interpreter (`value::checked_output`), the generated Rust (`checked_output` with `Returns::Values { name, values }`) and the generated JavaScript (`checkedOutput`). A tool output that does not fit the tool's declared return type is recorded as `failed("TOOL returned JSON, which is not a value of TYPE")` before its `result` record is written. It is not journaled as ok and then found corrupt, and no listed value stands in for it. The rule covers u64, bool and text results too ("which is not a u64", "a bool", "text"). The simulator never drew such results before, so every existing journal is unchanged. Arguments and journal values outside the enum keep the existing refusals: `hl run` and the generated `decode_arguments` / `argumentsFromJson` reject them, and a journal holding one is corrupt. `hl run --arg` takes a text enum argument as plain text.
- Rust names: a value that is not identifier-shaped becomes `X_` plus its alphanumerics, with every other character written as `_hex_` ("request changes" is `X_request_20_changes`). This keeps names injective: `camel` names never contain `_` except a keyword suffix, and no keyword starts with X. The emitted prelude allows `non_camel_case_types` for these names. Text enums derive `Default` with `#[default]` on the first value, which the derived `State::default` needs.
- Host API change: hosts that match `Returns` exhaustively need an arm for `Returns::Values`. `scripts/rust/drill_host.rs` and `sql_drill_host.rs` gained one.

Simulator:

- Arguments were already drawn uniformly over a sum's variants, so they now cover every value. ## 2026-11-14: fn blocks, inlined before checking (GAPS.md 4)

A harness can now share statements between handlers: `fn name(param: type, ...) { ... }` declares a block and the statement `name(argument, ...)` runs it. `examples/subagents.hl`'s model loop, written twice before, is one `fn model_loop()` that both `prompt` and `completion` call. `let name: type = expr` is new too, because it is how a call reads when written out.

How it works. `src/check/inline.rs` runs inside `check::check`, after constants, the model, types, tools and state are resolved and before invariants and handlers. It replaces every call with an `Inlined` statement that holds the fn's parameters, their arguments and the fn's body, already expanded. The checker turns an `Inlined` statement into `let param: type = argument` for each parameter, evaluated in the caller's scope, then checks the body with a scope stack that holds only the parameters. Lookups and the no-shadowing rule stop at that boundary, so a fn sees its parameters, its own bindings and the harness's declarations, and its names may repeat its caller's. The IR never contains a call. Effect sites, sequence numbers, the worst case, the prover, the emitters and the simulator are unchanged and remain per handler. The checker panics if a call reaches it: that is the pair assertion between the inliner and the checker.

Decisions:

- A fn has no value and no result type. A `return` in its body is a `return` of the handler that called it, checked against that handler's result type. A body that falls through continues after the call. The lowering has one finish per path and no early exit from a block, so a value-returning fn would need a new IR construct. The shared code in the nanocode ports, the model loop, ends the turn anyway. Using a fn inside an expression is an error that says so.
- Call by value, in written-out order. Each argument is evaluated in the caller just before its parameter is bound, which is the order a sequence of written-out `let`s gives. So locals, effect sites and their numbers come out in the same order, and the emitted code is byte for byte the same.
- Recursion. Fns are expanded depth first, in source order, with a stack of the fns being expanded. A call to a fn already on the stack reports the cycle from that fn's first entry, at the call that closes it: `fn 'ask' is recursive: ask -> run_tools -> ask`. Expanding every fn, not only those reached from handlers, finds recursion in a fn nobody calls as well.
- Every fn must be called. Only an inlined body is type-checked, so an uncalled fn would hide its errors.
- `fn` is a contextual word, like `below`, `calls`, `in`, `known` and `maybe`, not a keyword. It is read as `fn` only where an item starts, so a program that uses `fn` as a name still parses and `KEYWORDS` is unchanged.
- Bounds. A handler's blocks stay within `NESTING_DEPTH_MAX` (64) after inlining, since the checker, the prover and the emitters recurse under the same bound the parser enforces. A call that would go deeper is refused at the call, and so is a chain of calls longer than that. `STATEMENTS_PER_HANDLER_MAX` = 65,536 statements after inlining is policy. Fns that each call the previous one twice double the handler at every level: 40 of them, a file under 200 lines, would expand to about 2^41 statements. The largest example handler (reviewer.hl's `review_change`) has about 38. Reaching either bound is an error that names the bound.
- GAPS.md drops section 4 and keeps the other numbers, so references such as "GAPS.md 10" stay correct.
- New invalid examples: `examples/invalid/fn_recursion.hl` (mutual), `fn_arity.hl`, `fn_hidden_name.hl` (a fn reads its caller's parameter), all three required by check.sh. Doc snippets: `docs/snippets/errors/fn-self.hl` (direct recursion), `fn-expression.hl`, `fn-statement.hl` (a tool called as a statement) and `fn-unused.hl`.
- Departure from "a new invariant comes with a mutation the simulator catches". fn adds nothing at run time: every turn runs IR that a written-out program also produces, so there is no runtime invariant for the simulator to break. What fn does add is that a fn program lowers exactly as its written-out copy. `scripts/check.sh` checks this with `same_program`, which compares `hl emit` on all five targets and the whole `hl check` output (worst case and every proof, with file names masked). It compares `examples/subagents.hl` with `examples/inlined/subagents.hl`, which is subagents.hl exactly as it was before this change, and `docs/snippets/fn.hl` with `fn_inline.hl`. It also plants a bug: a written-out copy with two pushes swapped must check and prove but compare unequal.

- **The declared sum takes the builtin reply's slot.** It lives at `ir::REPLY` under its own name. A host reports a provider failure as `{"failed": text}`, the failed half of a result's output encoding. The `model` record holds what the host returned, unchanged as JSON. Decoding is the same function in the interpreter (`value::model_outcome`), the Rust runtime (`known_reply`) and the JavaScript runtime (`modelOutcome`). A one-key object `{"failed": string}` is `failed(text)`. A reply that decodes is `ok(reply)`. Anything else, including a list over the calls bound, is `failed("model reply: ...")`. It runs the body quietly from an iteration start that assumes them, keeps those still implied wherever the body falls through, and repeats until the set stops shrinking. That takes at most one round per invariant, the loop's bound. The survivors are assumed at the summary's start, at every iteration's start and at the exit. ## 2026-11-14: parallel tool calls: `for call in requested parallel`

GAPS.md gap 5 is closed and removed. `for call in requested parallel { match dispatch(call) { ... } }` runs a reply's calls at once, as nanocode's Claude backend does (`tool_batches` in `crates/backends/claude/src/agent.rs` at 395967f: consecutive parallel-safe calls form one batch, any other call is a batch of one; `exclusive` in `code_mode_policy.rs` marks `Write` and `Edit`). harnesslang reads "parallel-safe" from the effect class: none and idempotent calls group, an external call (a writer, and every undeclared tool) runs alone.

What it establishes:

- **Syntax and checking.** `parallel` is a contextual word after the list. The body is exactly one `match dispatch(item)` whose arms only `push` values that call no tool, model, `dispatch`, `now` or `random`; anything else is an error with its position: a statement other than that match ("found a let"), a match on anything but the item's dispatch, an arm that does more than push, and a parallel for inside another. The checker lowers the match as usual and then asserts the shape it produced; `ir::Stmt::Parallel` carries the item, list, bound, the one dispatch site, its result local and the push-only arms. `ir::validate` asserts the shape again. The worst case, finishing, arithmetic and fn-free text views read it as the plain `for` it equals (`Parallel::sequential`), so every count is unchanged: examples/claude_agent.hl keeps 1,280 effects, 2,499 journal records and 1,280 requests.
- **Order of a batch, the same in the interpreter, the generated Rust and the generated JavaScript.** (1) In list order each call takes the next sequence number and appends its `call` record, or is replayed from the journal; nothing is dispatched. (2) Groups run in list order; before an external group, and before every group on Cloudflare (the output gate), one flush makes the buffer durable, so the first external call finds every call record of the batch durable: durability point 1 once for the batch. Vercel reads the external call's step attempt after that flush exactly as for a single call (a reopened call on attempt 2 or later is reported unknown), and commits the step after its result. Each group's results are appended in list order whatever order they completed in. (3) The arms run in list order. So the records per sequence number are the plain loop's, calls of a batch ahead of its results. Consequence, by design: an external call of the batch whose record is durable is reported `unknown` after a crash even if the batch had not reached it yet; and a push that traps does so after every call of the batch ran.
- **Concurrency per target, from `src/target/`.** `Limits::concurrent_requests`: Cloudflare `CLOUDFLARE_CONNECTIONS_WAITING_MAX` = 6 (developers.cloudflare.com/workers/platform/limits, simultaneous open connections, which since the 2026-04-09 changelog count only while waiting for response headers; a seventh fetch is queued by the runtime, so the lowering keeps at most 6 in flight itself; read through a web search summary on 2026-11-14, like the other facts there); native and Vercel none (the list's capacity bounds the batch; Vercel documents no limit on concurrent steps, its limits are per run). The emitted programs carry it as `CONCURRENT_REQUESTS_MAX`. Native Rust: `World::tools` dispatches a group with `std::thread::scope`, at most the limit's worth of threads pulling indexes from an `AtomicUsize` and sending `(index, output)` over `std::sync::mpsc`, when the host returns `Some` from the new `Host::concurrent` (a `ConcurrentTools: Sync` it implements); hosts that do not (every existing host) run the group one call at a time through `Host::tool`, same journal. JavaScript: `dispatchConcurrently` runs a pool of `min(limit, n)` async workers under one `Promise.all` inside the Durable Object's event or the Vercel step.
- **Departure from the brief: Vercel runs a group inside the turn's step, not as parallel step functions.** In this lowering a step reruns the turn up to its next flush and the workflow records only what steps return. External calls already get one step each (they are groups of one, and the step commits after the result), so only none and idempotent calls run together, which are safe to run again when a step is retried. Separate step functions would give each its own retry and a result recorded on return, but need the workflow function to write result records itself; left for later.

Simulator. `World::tools(requests, limit)` returns outputs in completion order. `SimWorld` draws that order from `Rng::derive_keyed(seed, "batch", [turn, first seq, count])` as a pool of `min(limit, n)` would complete (the k-th completion is one of the started calls), records a `batch` trace event, and replays it through `run_batch`: a `before_run` hook as each call starts, an `after_run` hook as each completes, so a crash can land between any two of them with some calls dispatched and others not. The exhaustive explorer's world takes the default (list order) and so explores every crash point of a batch. New invariant `sequential_equal`: in every journal a turn's results appear in increasing sequence order, and on every clean seed of a program with a parallel for, the journal sorted per sequence number and the acknowledgements equal those of the same seed run with every parallel for lowered to its plain `for` (`Program::sequential`), unless that run trapped in a body (then the two legitimately differ). `external_once` holds per call, unchanged. The batch mutations are not in the prover's list, since `scripts/prove-mutations.sh` requires each listed mutation to fail agent.hl and reviewer.hl, which have no parallel for.

## 2026-11-14: tools from listing, typed tool input at dispatch, and Codex's end_turn

GAPS.md gap 6 is closed, and `examples/codex_agent.hl` declares its reply.

- **A listed family.** `tools from listing(NAME, BOUND) (PARAMS) effect CLASS` declares the tools a host lists at run time, named `NAME__TOOL` as nanocode names MCP tools `mcp__SERVER__TOOL` (395967f, `crates/backends/claude/src/agent/durable.rs:1750`). `ir::Program::listed` splits a name at its first `__`, so `dispatch_class` and `input_params` stay pure functions of the program and the name: the effect rule is still a compile-time fact, and the simulator, the oracle header and the invariants compute a call's true class without the journal. A listing's name may not hold `__` or end with `_` (it could never match), and a declared tool may not be named like a listed one; `ir::validate` asserts both again.
- **Admission is journaled.** `NAME()` is a `SiteKind::Listing` site of class `none` returning `known<u64>`. Its `call` record has the listing's name and a null input, and its `result` holds the listing as an object of tool name to fingerprint text, so no record kind changes and nanocode's fold reads it. A listing over `BOUND` or of another shape is recorded as the read's failure (the bound is the program's policy: TigerStyle's named bound on the admitted map). Each engine keeps the latest read per listing for the turn, rebuilt on replay from the same records. A failed read clears it.
- **Where the refusals happen.** A tool the latest read did not list is refused in the engine before anything is sent. A tool that changed since admission is refused by the host, which receives the admitted fingerprint in `ToolRequest::admitted` and compares it with the current definition, as nanocode's MCP host does (`crates/integrations/mcp-tools/src/native.rs:145`, `native_call_admitted`, "changed since admission; rediscover before executing"). The host owns the current definition, so the comparison costs no second request and cannot race the call. Both refusals are recorded failures, and a refused external call has the same records and flushes as a failed one, so the prover's plan and the worst case are unchanged.
- **Typed input.** A declared tool's parameters, or a family's, are its input type. `dispatch` decodes the call's `input` text, requires a JSON object holding exactly the parameters, each decoded with the same function a journal value is (`from_json`, the Rust `parse_*`, the JavaScript `fromJson`), and then journals that object as the call's input and sends it. Anything else is journaled as the text and recorded as `input of TOOL: ...` without running. An undeclared tool still receives the text. This changes what hosts receive for declared tools (an object instead of the text), so `scripts/rust/drill_host.rs`, `sql_drill_host.rs` and `bench_host.rs` now send JSON inputs, and the JavaScript host posts `admitted` with a listed call and listing reads to `HL_LISTINGS_URL`.
- **Simulator.** Each declared listing starts with each of the eight `WORDS` in `LISTED_PRESENT_PPM` = 500000 per million and changes at `begin_turn`, at every crash and at every model call, each name added, removed or re-fingerprinted in `LISTING_CHANGE_PPM` = 100000 per million (a keyed RNG, so programs without listings keep their fault draws). The model names a listed tool in `LISTED_TOOL_PPM` = 250000 calls, a name the listing may not hold in `UNLISTED_TOOL_PPM` = 250000 of those, and sends input that does not fit (not JSON, a parameter missing, one extra) in `INPUT_INVALID_PPM` = 100000 calls to typed tools. The world counts external dispatches by the program's class for the name, not the class the runtime sent. Valid inputs change the draws of every program: `hl sim --target native-jsonl --seeds 0..200 examples/agent.hl` went from dispatches=7785 unknown=746 to dispatches=7032 unknown=800, and LANGUAGE.md's and README.md's quoted lines were rerun.
- **Invariant and mutations.** `tool_admitted`: every tool with a declared input ran only with input that fits it, and the last run of each listed call had the fingerprint the journal's latest listing read before it admitted (the last run is the one whose records survive: a lost run's admission and call are lost together, and an external call's flush makes its admission durable). `unknown_reported` accepts an external call that records a result without a dispatch only when the invariant recomputes the same local refusal from the journal. Planted bugs, caught on every target in seeds 0..200 by `scripts/mutations.sh` on `examples/codex_agent.hl`: `listing_unchecked` (sends listed tools without their admission; tool_admitted at seed 0), `input_unchecked` (sends input that does not fit; tool_admitted at seed 0) and `listed_class_dropped` (journals an external listed tool as `none`; external_once at seed 0, "dispatched 9 times" on native-jsonl). They are simulator mutations, like `enum_unchecked`; no proved property depends on them.
- **Codex's end_turn.** The reply is `message(text, bool) | calls(list<call, calls_per_round_max>)`, the bool being `end_turn` with a missing value read as true, since `turn.rs:966` continues only on `Some(false)`. A message with `end_turn` false pushes the reply and starts the next round, as `turn.rs` `continue`s; true polls steering as before. A failed model call fails the turn, as `perform_model_call`'s error does. Each continuation spends one of `rounds_max` rounds, so the requires clause and the prover's bounds are unchanged. Each round first reads the `mcp` listing (external family, `mcp_tools_max` = 64), as Codex admits its tools per model request; a failed read admits nothing and the round goes on.
